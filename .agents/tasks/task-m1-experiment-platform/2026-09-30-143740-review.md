# Milestone 1: mock-first AgentCore compliance-remediation experiment platform (v1 review)

Milestone 1 stands up a pnpm/TypeScript monorepo where one shared contract package (`@agentcore2/contracts`) owns the finding/remediation/evidence/execution vocabulary, a `BackendAdapter` seam, a deterministic synthetic dataset (5000 findings, seeded PRNG, zero AWS calls), and a 7-agent planned catalogue; a Cloudscape "Preview A" app consumes only the adapter interface. Remediation is gated behind an approval dialog — reject appends a single `REJECTED` event with no mutation, approve appends the full `EXECUTED → PROVIDER_READBACK → CONFIG_CONVERGENCE → VERIFIED` chain with a persisted execution id. Provider readback and Config convergence are kept as distinct evidence kinds, and every screen shows a `MOCK` lab-mode badge so synthetic runs can't be mistaken for live evidence. The build, test (18 tests), and dev commands all run with no credentials.

Watch for: the approved-remediation chain is **not idempotent** — approving the same finding twice appends two full evidence chains and creates two SUCCEEDED executions, with no guard (confirmed). The documented evidence chain in `docs/ARCHITECTURE.md` includes a `FIX_PROPOSED` step that the mock adapter never actually emits (confirmed). Both are behavioral, not stylistic.

**Verdict**: NEEDS_CHANGES

## High-level view

The contract package is a genuine single source of truth. `apps/preview-a` imports every type and the `MockBackendAdapter` from `@agentcore2/contracts` and defines no domain types of its own; adapter construction is isolated to one file (`src/backend.ts`), so the mock→real swap touches exactly one line. This is the seam the milestone promised.

The approval gate is correct on a single pass and well tested, but the adapter has no notion of "this finding was already remediated." `requestRemediation` unconditionally appends to the finding's evidence timeline and stores a new execution every call. A second approve produces a second full chain and a second SUCCEEDED execution; the UI has no guard either (the Remediate button stays enabled after success). For a system whose whole point is trustworthy evidence, replayable mutation events are a real gap.

Evidence modelling honors the SPEC MUSTs: `PROVIDER_READBACK` and `CONFIG_CONVERGENCE` are separate `EvidenceKind`s, emitted as separate events, asserted distinct in tests. The one inconsistency is documentation: `docs/ARCHITECTURE.md` advertises a `DETECTED → EXPLAINED → FIX_PROPOSED → APPROVED → …` chain, but the adapter's approved chain starts at `APPROVED` and never emits `FIX_PROPOSED` — the kind exists in the type union and the timeline color map but is dead. Either the doc or the adapter is wrong.

Lab labeling is unmistakable: `adapter.mode()` returns `MOCK`, the badge renders in the header, and the mock adapter hard-codes `MOCK` for both findings and every execution's `mode` field, so a synthetic success carries the mock marker into its own execution record. Determinism is real — fixed base timestamps, no `Date.now()`, a seeded mulberry32 PRNG — and the dataset test asserts byte-identical output for a repeated seed.

The synthetic dataset uses placeholder account IDs (`000000000001`…), no real ARNs, no allowlist, no credentials anywhere; the `amplify.yml` and preview-strategy docs explicitly state the public repo carries no secrets or account allowlist. Adding a new experiment is documented as scaffold-copy-plus-`workspace:*`-dependency without duplicating the contract, which matches how Preview A is wired.

<details>
<summary>Issues (4)</summary>

1. **Non-idempotent remediation** — `requestRemediation` appends a full evidence chain and a new SUCCEEDED execution on every approved call, with no guard against a finding that was already remediated. Add an "already executed" check (return the existing execution, or emit a distinct no-op event) and cover it with a double-approve test.
2. **`FIX_PROPOSED` documented but never emitted** — `docs/ARCHITECTURE.md` shows `FIX_PROPOSED` in the approved chain, but the adapter never produces it; the kind is dead in the type union and the timeline color map. Either emit it (e.g. on `previewFix`/initial timeline) or remove it from the doc and the union.
3. **Shared mutable dataset objects leak from reads** — `previewFix`/`getRemediationForFinding` return the internal `Remediation` object by reference, and the internal timeline array is mutated in place by `requestRemediation`. Return copies from the read methods for parity with `getEvidenceTimeline`, which already copies.
4. **Reject/approve UI has no post-execution lockout** — after a SUCCEEDED or REJECTED result the Remediate button stays enabled, so the UI invites the non-idempotent replay above. Disable or relabel the action once an execution exists.

</details>

<details>
<summary>Details</summary>

### Approval gate is correct once, but replayable

The gate is right on a single invocation and precisely tested: `approve:false` writes a `REJECTED` execution, appends one `REJECTED` event, and emits none of the mutation kinds; `approve:true` writes SUCCEEDED and appends the full chain tagged with the execution id.

What's missing is any concept of terminal state. `requestRemediation` looks up the finding and remediation, then unconditionally allocates a new execution id and appends to the timeline:

```ts
const timeline = this.dataset.evidenceByFindingId.get(findingId) ?? [];
// ... no check for an existing SUCCEEDED execution on this finding ...
chain.forEach((entry, idx) => { timeline.push({ /* EXECUTED, READBACK, ... */ }); });
```

Approve the same finding twice and the timeline holds two `EXECUTED → … → VERIFIED` sequences and two SUCCEEDED executions with different ids. Nothing in the contract or the mock says a remediated finding is done. For a platform selling trustworthy evidence chains, duplicated mutation events on one resource is a behavioral defect, not cosmetic. The fix is a guard: if a SUCCEEDED execution already exists for the finding, return it (or append a single explicit no-op event) instead of replaying the chain. No test exercises a second call on the same finding, so this path is currently unobserved.

The UI compounds it: after `onDecision` sets an execution, the Remediate button's `disabled` is still just `busy || remediation === null`, so a reviewer can reopen the dialog and approve again.

### `FIX_PROPOSED`: documented, typed, never produced

`docs/ARCHITECTURE.md` prints the approved chain as `DETECTED → EXPLAINED → FIX_PROPOSED → APPROVED → EXECUTED → PROVIDER_READBACK → CONFIG_CONVERGENCE → VERIFIED`. The generator seeds `DETECTED` (+ `EXPLAINED` for non-compliant) and the adapter's approved chain begins at `APPROVED` — no code path ever emits `FIX_PROPOSED`. It's a member of the `EvidenceKind` union and has a color in `EvidenceTimeline`'s `COLOR_BY_KIND`, so it's a documented-and-typed event with no producer. A reader trusting the doc will look for a proposal event that never arrives. Resolve by either emitting `FIX_PROPOSED` when a fix is proposed/previewed or removing it from the doc and the union so the model matches behavior.

### Read methods hand out internal references

`getRemediationForFinding` and `previewFix` return the `Remediation` object straight from the dataset map, and `requestRemediation` mutates the internal timeline array in place. `getEvidenceTimeline` already defends itself by returning a copy (`[...]`); the remediation reads don't. A caller that mutates a returned remediation would corrupt the dataset for every later read. Low severity today because the UI treats them as read-only, but the asymmetry is worth closing for the same reason the timeline getter copies.

### Tests exercise real behavior

The 16 contract tests drive filtering (service, severity+status, free-text over ruleId), pagination boundaries (empty page past the end, no cross-page overlap), determinism, shape validity, and both remediation branches with exact event-kind assertions — they exercise the adapter's actual logic, not mocks of it. The two Preview A tests render the real `App` against a real `MockBackendAdapter`, click through a live row selection → Remediate → Approve flow, and assert an `exec-` id and a `CONFIG_CONVERGENCE` event appear in the DOM. The meaningful gaps: no test for the reject path in the UI, and no test for a repeated approve on the same finding — the exact path where the idempotency bug lives.

</details>
