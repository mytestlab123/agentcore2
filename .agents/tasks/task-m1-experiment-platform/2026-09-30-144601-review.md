# Milestone 1: idempotent remediation, FIX_PROPOSED producer, read-copy parity, UI lockout (v2 review)

Second-pass review of the M1 mock-first experiment platform (Issue #3). The v1 review returned NEEDS_CHANGES on four behavioral issues; commit `d5c8dea` addresses all four. The mock adapter now tracks a terminal SUCCEEDED execution per finding and treats any later `requestRemediation` on that finding as a no-op — re-approving returns the original execution and appends one explicit no-op event instead of replaying the mutation chain, and a reject on a terminal finding mutates nothing. The dataset seeds `DETECTED → EXPLAINED → FIX_PROPOSED` for non-compliant findings so `FIX_PROPOSED` finally has a producer, and `docs/ARCHITECTURE.md` was reconciled to that behavior. Read methods return copies, `requestRemediation` builds a fresh timeline array rather than mutating the stored one, and Preview A disables and relabels the Remediate button once an execution exists.

Watch for: the Preview A lockout keys on *any* execution, so a **rejected** finding also disables the Remediate button and cannot then be approved from the UI — the adapter still permits approve-after-reject, so UI and adapter disagree on whether reject is terminal (likely). Otherwise the four v1 issues are resolved and the SPEC MUSTs still hold; all 22 tests pass.

**Verdict**: APPROVED

## High-level view

All four v1 issues are fixed at the behavioral level. Idempotency is enforced in the adapter via a per-finding `succeededExecutionByFindingId` terminal-state gate, covered by tests asserting the mutation chain is not replayed and that a reject on a remediated finding returns the standing execution. The `FIX_PROPOSED` kind is now emitted by the dataset generator and asserted by tests, and the doc's chain diagram matches. Read-copy parity is closed: `getRemediationForFinding`/`previewFix` spread-copy and `requestRemediation` rebuilds the timeline array instead of mutating the stored one.

The remaining observation is a UI/adapter mismatch on what "terminal" means. The adapter treats only SUCCEEDED as terminal (approve-after-reject still runs the full chain), but the button disables on any non-null execution including REJECTED — so a user who rejects can no longer approve from Preview A without reselecting the finding. This is a minor UX inconsistency, not a correctness or safety defect, since the adapter's mutation semantics remain correct on every path.

No regression to the SPEC MUSTs: `PROVIDER_READBACK` and `CONFIG_CONVERGENCE` remain separate evidence kinds emitted as separate events (asserted distinct), every execution carries `mode: "MOCK"`, timestamps are deterministic with no `Date.now()`, the synthetic dataset uses placeholder account IDs with no allowlist or credentials, and the shared contract still powers both the adapter and Preview A through a single construction point. No synthetic success is dressed up as live evidence — the no-op event is a `VERIFIED`-kind entry whose summary explicitly says the finding was already remediated and no action was taken.

<summary>Details</summary>

### Idempotency is enforced in the adapter, not just the UI

The terminal-state gate is a `succeededExecutionByFindingId` map, set only after a successful approved chain completes. On entry, `requestRemediation` checks that map: if the finding already has a SUCCEEDED execution, it returns that execution and — for an approve — appends exactly one no-op event without allocating a new execution id or touching the mutation chain. The guard sits in the adapter regardless of caller, so the UI lockout is defense-in-depth rather than the sole protection. The double-approve test asserts the second call returns the same `executionId`, the timeline grows by exactly one event, and `EXECUTED`/`PROVIDER_READBACK`/`CONFIG_CONVERGENCE`/`APPROVED` counts each stay at 1 (confirmed).

The no-op event is modelled as a `VERIFIED`-kind event with actor `agent-evidence-report` and summary "Finding already remediated; re-approval is a no-op. Existing execution stands." It references the original `executionId`, so it can't be mistaken for a fresh mutation. Its timestamp derives from `executionCounter` without incrementing the counter, so a repeated no-op reuses the same base value; this is deterministic and harmless (the events are ordered by array position, not timestamp) but means two successive no-ops on one finding would carry identical timestamps — worth knowing, not worth fixing at M1 (possible, low impact).

### Reject-on-terminal is a no-op, but UI and adapter disagree on reject semantics

A reject (`approve:false`) on an already-remediated finding returns the standing SUCCEEDED execution and mutates nothing — no REJECTED execution or event is produced; the test confirms the timeline length is unchanged and no REJECTED event appears (confirmed).

The asymmetry is on a *non-terminal* finding. The adapter treats only SUCCEEDED as terminal, so a finding that was rejected can still be approved later (the reject wrote a REJECTED execution but did not set the terminal map). The Preview A button, however, disables on `busy || remediation === null || execution !== null` — any execution, including REJECTED, disables it. So from the UI a rejected finding shows "Remediation recorded" and can no longer be approved without reselecting, even though the adapter would happily run the chain. Nothing breaks, but the two layers encode different notions of "done." Keying the button on a SUCCEEDED status (or making the adapter treat reject as terminal) would align them (likely).

### FIX_PROPOSED now has a producer and the doc matches

The dataset generator appends a `FIX_PROPOSED` event (id `-ev-2`, actor `agent-finding-triage`) after `EXPLAINED` for every NON_COMPLIANT finding, so the initial timeline is `DETECTED → EXPLAINED → FIX_PROPOSED` and the kind is no longer dead in the union or the timeline color map. `docs/ARCHITECTURE.md` was rewritten to show `FIX_PROPOSED` as part of the seeded initial timeline and the approved chain as the appended `APPROVED → … → VERIFIED` segment, and to document idempotency. The dataset test asserts the exact three-kind initial sequence for non-compliant findings plus a broader "some finding emits FIX_PROPOSED" check (confirmed). Doc and behavior now agree.

### Read-copy parity closed

`getRemediationForFinding` and `previewFix` return `{ ...remediation }`, and `requestRemediation` opens with `[...(evidenceByFindingId.get(findingId) ?? [])]` on every branch, rebuilding the array and writing it back with `set` rather than pushing into the stored reference. The read-copy test mutates a returned remediation's `title` and confirms a later read is unaffected, and checks that two reads return distinct object identities with equal contents (confirmed). The v1 leaked-reference asymmetry with `getEvidenceTimeline` is gone.

### Tests exercise the new paths, not stubs

The four new contract tests drive real adapter logic: double-approve no-op (same execution id, single appended event, mutation-kind counts pinned at 1), reject-after-success no-op (standing execution returned, zero mutation), read-copy isolation (mutation of a returned copy doesn't corrupt later reads), and FIX_PROPOSED emission (exact initial-timeline sequence). The preview-a test now clicks through select → Remediate → Approve and then asserts the button is `disabled` and reads "Remediation recorded", which is the exact UI replay path v1 flagged as unguarded. Contracts moved 16 → 20 and preview-a's approve test gained the lockout assertion; the full suite runs 22 green with no credentials.

Not tested: the reject path through the UI (the reject-then-locked-button behavior above is unasserted, so the UI/adapter mismatch isn't caught by a test), and a repeated no-op on the same finding (the identical-timestamp edge). Neither is a correctness gap at M1.
